## Independently OPEN launcher → kernel-open result edge

The launcher-selected **opened FD/object** does not, by itself, identify the **actual file returned by kernel exec open**. In [`fs/exec.c:764–803`](https://github.com/torvalds/linux/blob/v6.16/fs/exec.c#L764-L803), `do_open_execat` accepts `AT_EMPTY_PATH` as `LOOKUP_EMPTY` and obtains its executable file from `do_filp_open`. In [`fs/namei.c:4074–4089`](https://github.com/torvalds/linux/blob/v6.16/fs/namei.c#L4074-L4089), `do_filp_open` delegates the open to `path_openat`; that path does **not promise pointer equality or object/provenance identity to the launcher FD**. [`alloc_bprm`, `fs/exec.c:1404–1421`](https://github.com/torvalds/linux/blob/v6.16/fs/exec.c#L1404-L1421) initially sets `bprm->file` to the **kernel-opened result**, not a proven launcher-owned object. This evidence does **not** assert a distinct `struct file` was necessarily reopened; it also does **not** assert pointer equality. An FD number, pathname, inode, digest or equal bytes is not a provenance join. Even exact immutable content does not prove which opened object the kernel selected. The launcher-object → kernel-opened-result edge remains independently **OPEN**, in addition to EXPECTED → selected object and object → exec success.

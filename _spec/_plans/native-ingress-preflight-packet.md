## Common gate for **each** future request, including each subrequest below

Before any operation, a lead must present a *new*, individually reviewable, exact proposal for its single permission class and named target(s). Its approval must explicitly identify the human approval decision and approved identity; selecting this design, a prior review verdict, an earlier grant or approving another class is insufficient. Each proposal must state **before the run**:

1. Exact target absolute paths or already-owned handles, each approved operation/read and its purpose, source of independent EXPECTED values chosen **before** observations, and how the controller binds observations to those targets. A discovered path, worker claim, daemon response or generated digest cannot set its own expected value. Distinguish approval to resolve a handle from approval to read bytes through it; neither implies permission to enumerate parents or open another file.
2. Exact entry and controller *bytes and SHA-256 identities*, trust and startup-effects assumptions, proposed safe observation interface, caller/harness behavior and side effects (including incidental startup, filesystem, daemon and kernel effects). Bind the entry/control snapshot immediately before any separately approved use; an earlier prepared snapshot is not an execution grant. Unavailable interfaces or unknown installed behavior STOP rather than prompt a fallback.
3. One attempt per named request/target (**attempt count = 1**) unless another attempt receives its own separate exact approval. Specify finite **per-target byte limits and operation counts**, aggregate captured stdout+stderr/retained-output limit and outer wall-clock bound, failure/cleanup limits, and any write or descendant effects. Select quantities from independently reviewed current evidence, **not** H02/M2 ceilings, old timeouts or this design. A controller/library buffer cap or timeout request is not proof of all physical effects or absolute process-tree termination.
4. A raw-data/redaction/retention plan: who receives each field and when, whether sensitive bytes may be encountered, how it is classified and redacted, and bounded retention/storage and disposal subject to explicit approval. No secret, credential, private control, raw daemon body, raw receipt or process memory is released to the requester by default. A status/count is not authority; redaction cannot silently discard evidence needed to decide STOP.
5. Precise STOP rules for missing, denied, partial, inconsistent, truncated, oversized/overflowed or drifting targets, outputs, reference identities, side effects or prerequisites; no alternate pathname, PATH search, retry, reinterpretation of partial results, loosening policy or automatic transition to the next class. Stop before further effects where possible; report only the approved bounded/redacted diagnostic. Failure does not authorize cleanup reads, deletions or another probe.

The approved request must name its **own class**; the common gate applies afresh to (0), each named read in (1), each chosen realm/process target in (2), each daemon/init subrequest in (3), each kernel/graph subrequest in (4), and each distinct offline/live operation in (5). Approval of a read-only class never approves a build, container launch, daemon call or Native verification. No new privileges, sudo, proc mount, daemon socket mount, network access, posture change, fallback acquisition or unbounded traversal is implicit.
